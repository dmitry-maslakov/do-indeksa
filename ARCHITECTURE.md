# Architecture

Do indeksa is one Next.js app. Pages render on the server and call feature code directly, writes go through server actions, and the few reads the client drives go through GET route handlers. The one write outside actions is `POST /api/events`, which takes analytics batches from the browser: they are sent with `keepalive` when the page is hidden or closed, and a server action cannot do that. Postgres holds only what students do. Topics, exams, tasks, variants and theory are Markdown files compiled into the build.

Filters, sort and search live in the URL through nuqs. The bank's topic is a path segment, `/bank/topic/<topic>`, so the build prerenders a shell for every topic. `bankHref` builds the bank links that carry filters, and the proxy sends old `/bank?topic=` links to the topic path with a 308. Lists that grow on the client, the bank feed and the test history, fetch further pages with TanStack Query from a route handler that parses its input with the same parsers as the page, and the server renders the first page. Bank cards carry their statement as HTML from the server renderer, so the browser has no Markdown stack. They are the same for every student, so the shell already shows the first cards of its topic without the query filters, dimmed after a client navigation until the list for the full address streams in. The student's marks and recommended task stream in next to them, and the bank keeps its loaded pages when the student comes back to it. The first page holds three cards and the next ten load right after it.

A task page needs only its address to render the statement and the answer field, so Next prerenders that part once per address and keeps it in its memory cache, 50 MB per server by default. The build prerenders the `sr-Latn` shells of the exam tasks and of each topic's 25 easiest other tasks, which a new student's queue serves first, and a server reads them from disk on a cache miss. Any other address prerenders on its first visit to each server. Each shell adds about 130 KB to the image, so the list takes a fixed number of tasks per topic and grows only with exam tasks. The student's next task and past result on the task stream in afterwards through Suspense, and links to a recommended task prefetch the statement before the click. The home page works the same way: the weekly card, topic names and exam years are in the prerendered shell, and the suggestion and topic progress stream in. The list of tasks beside a task lives in the bank layout, above the task page, so it stays mounted when the student moves to another task. The page hands it its queue promise, and the list marks the task from the address at once and swaps in the page's queue when it arrives. It shows a skeleton only on the first load and when the topic changes. It lists the tasks of the visit with how each went, a count of them above, and the first three upcoming rows; the open task is marked, and the first upcoming row, which the next-task button leads to, is labelled. A page shown again from history refreshes, so the list and its next-task button come from the same queue.

Pages with nothing personal, theory, privacy and terms, are prerendered whole and served from the cache with `s-maxage`. The shared layouts read no cookie or header, because one such read anywhere in them makes every page render on each request.

Cloudflare serves `/_next/static` on doindeksa.rs from the R2 bucket `do-indeksa-static` through a Cloud Connector rule, not from the pods. CI uploads the static files of every trusted build before the image is tagged, and the bucket keeps the files of all builds. During a rollout two builds run side by side, so a page always finds the scripts and styles of the build that rendered it, and so does a tab opened before the rollout.

## Code map

`content/` is a small public sample. Production builds read the private bank instead, through `CONTENT_DIR`, and content-collections validates both against the schemas in `content-collections.ts`.

A task's `check` lists the parts its answer field asks for. Each part has the `expected` LaTeX and may add:

- `part`: the letter of the part in the statement, written as `**a)**` there. Latin and Serbian lettering both work: `a`, `b`, `v`, `g`, `d`, `đ`, `e`. The build rejects a letter the statement does not have. Several checked parts can share a letter.
- `var`: the unknown the part asks for, as TeX without dollar signs: `x`, `m`, `(x, y)`, `|z|`.
- `kind`: `value` (one number or expression, shown as `x =`), `values` (one or more values in no order, such as roots, shown as `x ∈ { }`), `interval` (an interval, a union or isolated points, shown as `x ∈`, or `D =` when `var` is one capital letter, optionally with an argument or index such as `D(f)`), `point` (an ordered tuple, shown as `(x, y) =`; a list whose order matters, such as the terms of a sequence, is written as a tuple) or `points` (tuples in no order, shown as `(x, y) ∈ { }`). The build rejects a kind that does not fit `expected`: `values` is a comma-separated list, `point` is a tuple, `interval` is brackets joined by `\cup` with an open bracket at each `\infty`, and `\emptyset` fits `values` and `interval`. When `var` is a tuple, `expected` must be tuples with as many components, whether or not `kind` is given.
- `unit`: TeX shown after the field, which the student does not type.
- `label`: a caption over the field, Serbian text with TeX only inside `$…$`.

Without `kind`, the kind is read from `expected`: `\cup`, `\infty` or `\{` in it, or a square bracket at the end of a pair, make an interval, three or more components a point, a list of tuples points and any other list values. A bare pair `(a, b)` and `\emptyset` stay unread and are shown with `=`. Without `var`, a `label` of up to 8 characters without spaces, or one ending in `=` of up to 18 characters, is read as the unknown, so a short caption needs `var`. `answer` is optional: without it the result is built from `check`. `keyRev` hashes `expected` only, so these fields never change it.

Theory is `theory/<topic>/index.md` with `##` sections plus `theory/<topic>/methods/<slug>.md`, and uses the blocks `:::remember`, `:::example`, `:::mistake` and `:::formulas`. Each topic lists its task types in `types` and every task names one in `type`: the slug of the method that is the key to solving it, or a kind of task that no method covers.

A weekly variant is `variants/nedelja-<Monday>.yaml` with tasks `nedelja-<Monday>-01` to `-10`, each of difficulty 3 or more. During its week it is Varijanta nedelje; the home page caches the card for up to an hour, so a new week can start with the old card. Until the bank marks it `released: true`, its tasks stay out of the bank list, search, practice and the sitemap, though each still opens by its link; once released, the variant joins the curated tests. A week with no variant of its own takes a curated test in turn.

`messages/` has the UI strings for `sr-Latn`, `ru` and `en`.

`src/app` holds routes. A `page.tsx` sets metadata, layout and Suspense boundaries, and whatever loads or renders data for one route sits next to it in `_components`. The app shell, with navigation and footer, is in `(app)/_components/shell`. Pages sit in route groups by how much of it they show on a phone: `(site)` all of it, `(read)` theory topics without the header, `(task)` a task and `(exam)` a test with neither the header nor the bottom bar. Each group's layout renders the shell for its mode, so the server sends the final chrome. `src/app/api` has route handlers for auth, the bank feed, the test history, task reveals, analytics events and the health check.

A page cannot change its status once its shell has streamed, and the chrome is part of the shell. So `src/proxy.ts` answers 404 for a task, theory topic, method or variant id that the content does not have, by rewriting to the not found page. Test and set codes live in the database, so their pages check them. The review links to and shares a composed test by its code. An old `/variants/set-…` link redirects to the code of its set and saves the set only if it was never saved. The not found page itself, reached through `notFound()`, still arrives with an empty body that fills in once scripts run, so only its status and `noindex` come from the server.

`src/features` has the product code. Each folder owns its server code, one `actions.ts`, its components and its hooks:

- `catalog` reads content: exams, topics, tasks and the answer checker.
- `progress` turns attempts into task status, topic status and statistics. The pure learning model and the policy that holds its numbers live in `progress/learning`: the topic status, the ability per topic (an Elo over first attempts, where a new topic starts from the others) and the planner, which scores candidate tasks or topics with a list of weighted signals and names the strongest one as the reason for each pick. A topic is mastered only with clean results in three of its task types, or in all of them when the bank serves fewer, and helped results don't count. The `newType` signal nudges the planner toward a task whose type has no clean result in the topic's window yet. Repeats are a projection too: `progress/learning/repeats` splits every attempt at a task, in any session, into tries by the same sitting rule and gives each the same result as an observation, and the last try sets when the task is due again. The planner offers due tasks through the `repeatDue` signal, and its rules, which veto a candidate before scoring, keep repeats to two in every six tasks and near the topic's level, with at most one stretch above it a day, counted from the task history, and none while a near due task is left among the plan's candidates. A repeat never feeds the ability or the status. `progress/attempt-log.ts` reads the attempt log, and `buildLearning` in `progress/learning/build-learning.ts` folds it into the student's state: status, ability, tasks today and the current fail streak per topic, and the last result, last try and due time per task. The fold is a pure function of the log and a moment, so `learningAsOf` rebuilds the state as it was at an earlier moment from the same read, and `getLearning` in `progress/student-learning.ts` is the shared read for the present. Today's suggestion on the home page is a planner decision over topics, made in `progress/topic-progress.ts` with the topic signals.
- `practice` is working on one task: the answer field, hints and solutions, task sessions and reports.
- `bank` is the task list with filters, search and the queue of what to solve next. A visit is the run of a student's touches of tasks in one topic, each starting less than an hour after the previous one ended, whose last touch ended less than an hour ago; a touch is a task session, and touches in tests don't count. The task page lists the visit's tasks by their first touch, with the open task last when it was not touched yet, and then six upcoming rows that the planner picks from the new tasks and the due repeats of the topic, of which the list shows three. A task of the visit is never an upcoming row, and the list holds nothing from earlier visits. `bank/queue` replays the visit instead of storing it: it plans the rows as of the start of the visit, and every touch since then, in time order, removes its task from the rows and tops them up at the bottom with the state of the student as of that touch, which `learningAsOf` rebuilds from one read of the log. Rows already shown keep their place until the student takes them, and an answer or a second visit to a task of the visit changes nothing; new rows come only with the next task the student opens. Outside a visit the home page and the bank start a topic with the planner's first pick, and during a visit with the first upcoming row.
- `variants` lists exam variants, the weekly one and variants composed from chosen topics. Composing a test, practicing similar tasks and swapping a task go through actions that save the set of tasks and redirect to its code at `/v/<code>`, so the test arrives in the same response. Next does not report an action's redirect as a router transition, so the caller reports the navigation to analytics itself.
- `tests` runs a variant as a test, grades it and shows the review.
- `theory` renders theory pages.
- `account` is Google sign-in, the prompts that ask a guest to save their progress, and merging a guest into an account.
- `launch` keeps the site closed before launch: without the access cookie only the landing, privacy and terms pages open.

`catalog` imports no other feature. `progress` builds on `catalog`, `practice` on both, `bank` on all three. `variants` builds on `catalog`, `tests` on `variants` and `practice`, `account` on `tests`. Biome rejects an import that goes the other way.

`src/components` is UI shared by several features, with shadcn in `components/ui`. `src/lib` is helpers that know nothing about exams or students. `src/db` has the Drizzle schema, the column types, shared SQL helpers and the migrate and cleanup scripts. `src/server` is infrastructure: the database client, env, auth, the current profile, the action clients and the analytics sinks. None of these import features or routes.

## Invariants

Nothing checks these automatically.

### Answers stay on the server

A task page gets the statement and the part labels. A server action checks answers with Compute Engine. The page fetches hints, the key and the solution one at a time from `/api/tasks/[id]/reveal` when the student opens them, and an action saves each opening as a reveal. For the key and the solution the endpoint also returns the expected LaTeX of every checked part, which the page puts into the answer fields. The fields then lock, as they do for a correct part; a hint leaves them open.

### Everything belongs to a profile

A profile is the student, and the better-auth user is only how they sign in. Task and test sessions, attempts, reveals, skips, suggestions and reports all point at `profiles.id`. A guest gets a profile on their first action, keyed by a random token in an httpOnly `__Host-profile` cookie whose hash is stored. That cookie never opens a profile that has a user. An account without a profile uses the guest profile until it takes it over, or gets its own on its first action when there is no guest, so rendering a page never creates a profile.

Feature functions take the profile id as an argument and scope every query to it. The id comes from `src/server/profile.ts`, from the session or the cookie, never from request input.

When someone signs in while holding a guest cookie, the account takes over the guest profile. Sign-in sets a short-lived readable cookie for this, and the first page that loads after it runs the merge from the browser. If the account already has a profile, the guest's sessions, reports and suggestions move into it and the guest profile is deleted. Session foreign keys cascade on update, so attempts, reveals and skips follow their sessions. A scheduled job deletes guest profiles idle for 30 days, or for 400 days if they have attempts or tests. Deleting an account puts its profile id in `analytics_erasures`, and the same job then deletes the analytics of that profile, of the guest profiles merged into it and of the browsers it was used in: the events in ClickHouse and the rows in every OpenPanel table the cleanup user is granted.

### A sitting on a task is a task session

The server keeps task sessions. While the page is visible it pings every 30 seconds. A ping, attempt or reveal within 45 seconds of the previous signal extends the session, so one late ping doesn't split a sitting; a later one opens a new session. Time on a task is `last_seen_at − started_at` on the database clock.

In practice a session is `first` until the task has been worked on, meaning an answer with a part right or wrong or an opened answer or solution, and an hour has passed since the last attempt, reveal or skip on it; after that it is `retry`. A hint, an empty or unreadable answer or a skip alone leaves the first attempt open. A reload or a short break doesn't count as a second try. In a test it is `mock`. Each attempt stores the task's difficulty, a hash of its key and the checker version, so results can be recomputed when content or grading changes. The action client refuses crawlers by User-Agent, so they never get a profile.

The task page, `checkAnswer` and the statuses read a sitting through the same `sittings()` as the learning model, with the same hour of silence. A right answer, an opened answer or an opened solution closes the sitting: the page restores the lock, the opened cards and the solved parts after a reload, and `checkAnswer` records no more answers in it. A hint opened alone is restored for an hour and locks nothing; a right answer given under a replaced answer key locks nothing. An answer given after an opened answer or solution in the same sitting, old data included, counts for no task status, statistic or bank filter.

### A test is a draft until it is finished

A running test lives in the browser (zustand with localStorage) and is saved as a draft in its `test_sessions` row, so it survives a reload or a switch to another device. The draft is never graded and stays out of history and statistics.

Finishing is one transaction: each visit to a task becomes a `mock` task session, the answers are graded into attempts, the draft is cleared and `finished_at` is set. The client picks the test id, so a second submit changes nothing. The finish action refreshes the page and redirects to the review, which arrives in the same response, and the runner drops its local copy of the test when the action rejects with that redirect. The score is points times the share of correct parts. It is practice feedback and says nothing about how FTN would grade the same work.

### Task ids never change

Attempts refer to task ids, so CI fails a pull request that renames or deletes a file under `content/tasks`.

Pull requests build and test with the public `content/`. Builds of `main`, including the hourly one, bake in the bank's `main`. The bank's CI validates it against the app's `main`, so a change to the content format lands in the app first, together with `content/`, and then in the bank. Until the bank catches up, builds of `main` fail and production keeps the previous image.
